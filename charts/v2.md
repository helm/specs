## 1. Introduction

A Helm *chart* is a package of files that describes a set of Kubernetes
resources. A chart holds metadata, default configuration values, templates that
render to Kubernetes manifests, optional Custom Resource Definitions, and
optional dependency charts.

This document specifies charts whose `Chart.yaml` declares `apiVersion: v2`.
Helm 3 introduced this version, and Helm 4 still uses it. Use this document to
build tools that create, read, validate, lint, package, render, or change these
charts. Examples of such tools are linters, editors, IDE plugins, chart
generators, security scanners, documentation generators, and AI agents.

### 1.1 Scope

In scope:

* The file and directory layout of a chart.
* The format and meaning of `Chart.yaml`, `Chart.lock`, `values.yaml`,
  `values.schema.json`, `.helmignore`, `templates/`, `crds/`, and `charts/`.
* How values are merged, how dependencies are enabled, and how values are
  imported.
* The template rendering model: built-in objects and functions.
* Hook and test annotations, and how resources are ordered.
* The packaged chart archive (`.tgz`) and the provenance (`.prov`) file.
* Validation and lint rules.

Out of scope:

* Chart API `v3`. This document does not describe it.
* Chart API `v1` (Helm 2). It appears only where `v2` tools must stay
  compatible with it (see [Appendix D](#appendix-d-differences-from-chart-api-v1)).
* Chart repositories (`index.yaml`) and OCI registry distribution. These are
  mentioned only where a chart refers to them. They are expected to have their
  own specifications.
* How Helm stores releases in a cluster.

### 1.2 Sources

This specification comes from three sources:

1. The Helm source code on the `main` branch. This is the **normative**
   reference. Where the code and the documentation disagree, this
   specification describes what the code does and records the difference in
   [Appendix E](#appendix-e-known-documentation-and-implementation-differences).
2. The Helm documentation (`helm/helm-www`), mainly *Charts*, *Chart Hooks*,
   *Built-in Objects*, *Library Charts*, *Chart Tests*, *Provenance*, and the
   *Chart Best Practices Guide*.
3. A survey of 190 public `apiVersion: v2` charts from widely used
   repositories (Bitnami, prometheus-community, Grafana, ingress-nginx,
   Argo, cert-manager, Traefik, Elastic, OpenTelemetry, external-dns). The
   survey shows how charts use the format in practice. Its findings are
   marked *Observed practice* and are not normative.

## 2. Conventions and Terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in
[BCP 14](https://www.rfc-editor.org/info/bcp14)
([RFC 2119](https://www.rfc-editor.org/rfc/rfc2119),
[RFC 8174](https://www.rfc-editor.org/rfc/rfc8174)) when, and only when, they
appear in all capitals, as shown here.

Requirements apply to two kinds of things:

* A **chart** (the author's output). For example: "A chart MUST contain
  `Chart.yaml`."
* An **implementation** (a tool that reads, writes, or renders charts). For
  example: "An implementation MUST reject archive entries with absolute
  paths."

Terms:

| Term | Meaning |
|---|---|
| Chart | A directory or archive that follows this specification. |
| Chart root | The directory that contains `Chart.yaml`. All chart paths are relative to it and use `/` as the separator. |
| Parent chart | A chart that has other charts in its `charts/` directory. |
| Subchart / dependency | A chart inside the `charts/` directory of a parent chart. It can be a directory or a `.tgz` archive. |
| Top-level chart / root chart | The chart that a user installs or renders directly. It has no parent. |
| Application chart | A chart with `type: application` or no `type`. It can be installed. |
| Library chart | A chart with `type: library`. It only provides named templates and cannot be installed. |
| Release | One installation of a chart in a cluster, with a name. |
| Values | A tree of configuration data (a YAML map) that templates use. |
| Manifest | One rendered Kubernetes resource document. |
| Hook | A manifest with the `helm.sh/hook` annotation. Helm runs it at a lifecycle point instead of installing it with the other manifests. |
| SemVer | [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). |
| Masterminds semver | The Go library [`github.com/Masterminds/semver/v3`](https://github.com/Masterminds/semver). Helm uses it to parse versions and version ranges. |

Unless a section says otherwise, all YAML files are UTF-8. An implementation
MUST strip a leading UTF-8 byte order mark (`EF BB BF`) from every chart file
before it processes the file.

## 3. Chart Structure

### 3.1 Directory Layout

A chart is a directory tree. A packaged chart is an archive of that tree (see
[Section 14](#14-chart-archive-package-format)). This is the layout:

```text
mychart/
  Chart.yaml          # REQUIRED. Chart metadata.
  Chart.lock          # OPTIONAL. Locked dependency versions.
  values.yaml         # OPTIONAL. Default configuration values.
  values.schema.json  # OPTIONAL. JSON Schema for the values.
  charts/             # OPTIONAL. Dependency charts (directories or .tgz files).
  crds/               # OPTIONAL. Custom Resource Definitions. Not templated.
  templates/          # OPTIONAL. Templates that render to Kubernetes manifests.
    NOTES.txt         # OPTIONAL. Usage notes shown after install or upgrade.
    _helpers.tpl      # OPTIONAL. Partials (named templates). Not rendered alone.
    tests/            # OPTIONAL. By convention, test hook templates.
  .helmignore         # OPTIONAL. Patterns to leave out when packaging.
  README.md           # OPTIONAL. Human-readable documentation.
  LICENSE             # OPTIONAL. License text.
```

The name of the chart directory has no meaning. A chart's identity is the
`name` field in `Chart.yaml`. By convention, the directory has the same name
as the chart. When Helm packages a chart, it uses the chart name as the
top-level directory in the archive.

### 3.2 Reserved Paths

An implementation that loads a chart MUST put each file into one of the
categories below. The check uses the file's path relative to the chart root.
The first rule that matches wins.

| Path | Category | Notes |
|---|---|---|
| `Chart.yaml` | Metadata | REQUIRED. If it is missing, loading MUST fail. |
| `Chart.lock` | Lock | Parsed as a lock file ([Section 6](#6-chartlock)). |
| `values.yaml` | Default values | Parsed as values ([Section 7](#7-values)). Only the exact name `values.yaml` is special. `values.yml` is an ordinary file. |
| `values.schema.json` | Values schema | Kept as raw bytes ([Section 8](#8-valuesschemajson)). |
| `requirements.yaml` | Legacy dependencies | A `v1` file. See [Appendix D](#appendix-d-differences-from-chart-api-v1). |
| `requirements.lock` | Legacy lock | A `v1` file. See [Appendix D](#appendix-d-differences-from-chart-api-v1). |
| `templates/**` | Templates | Every file under `templates/`, at any depth. |
| `charts/*.prov` | File | Provenance files for packaged subcharts. Kept as ordinary files. |
| `charts/<entry>/**` or `charts/<entry>.tgz` | Subchart | See [Section 3.3](#33-the-charts-directory). |
| anything else | File | Ordinary files, available to templates through `.Files`. This includes `crds/`, `README.md`, `LICENSE`, and `.helmignore`. |

The file names above are case-sensitive.

### 3.3 The `charts/` Directory

Each entry directly inside `charts/` is a subchart:

* A **directory** `charts/<dir>/` MUST be a chart. It MUST contain
  `Chart.yaml` at `charts/<dir>/Chart.yaml`.
* A **file** whose name ends in `.tgz` MUST be a chart archive
  ([Section 14](#14-chart-archive-package-format)).
* An entry whose name starts with `_` or `.` MUST be ignored. Authors can use
  this to keep a chart in `charts/` without loading it.
* A file whose name ends in `.prov` is a provenance file. It is kept as an
  ordinary file and is not loaded as a chart.

Any other plain file directly inside `charts/` (for example `charts/README.md`)
makes loading fail in the reference implementation. Charts MUST NOT have such
files.

Helm loads subcharts recursively, so subcharts can have their own `charts/`
directory. A subchart is identified by the `name` in its own `Chart.yaml`, not
by its directory or file name.

### 3.4 Symbolic Links and Special Files

When Helm loads a chart from a directory:

* It follows symbolic links, including links to directories. It logs a
  warning for each one, because a symlink can point outside the chart.
* It MUST fail on irregular files, such as devices, sockets, and named pipes.
* It applies `.helmignore` rules ([Section 13](#13-helmignore)) before it
  reads files.

A chart archive contains only regular files ([Section 14](#14-chart-archive-package-format)).
Symlinks become their content when Helm packages a chart.

*Observed practice:* Besides the files in Section 3.1, public charts often
have `ci/` (values files for CI test matrices, 45 of 190), `CHANGELOG.md`,
`README.md.gotmpl` (helm-docs input), `unittests/` or `tests/` (helm-unittest),
`files/`, and `examples/`. All of these are ordinary files to Helm. Authors
SHOULD list development-only files in `.helmignore`.

## 4. Chart.yaml

`Chart.yaml` is REQUIRED. It is a YAML document whose top level is a map. It
holds the chart metadata.

### 4.1 Detecting the API Version

An implementation MUST read `apiVersion` before it interprets the rest of the
file:

| `apiVersion` value | Meaning |
|---|---|
| `v2` | The chart follows this specification. |
| `v1` | A Helm 2 chart. Helm still reads it for compatibility. |
| missing or empty | Treated as `v1`. |
| `v3` | A different chart format. Out of scope for this specification. |
| anything else | Unsupported. Loading MUST fail. |

A chart that follows this specification MUST set `apiVersion: v2`.

### 4.2 Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `apiVersion` | string | **yes** | The chart API version. MUST be `v2`. |
| `name` | string | **yes** | The chart name. See [Section 4.3](#43-name). |
| `version` | string | **yes** | The chart version, a SemVer string. See [Section 4.4](#44-version). |
| `kubeVersion` | string | no | A SemVer range of Kubernetes versions the chart supports. See [Section 4.6](#46-kubeversion). |
| `description` | string | no | A one-sentence description of the chart. |
| `type` | string | no | `application` (the default) or `library`. See [Section 4.7](#47-type). |
| `keywords` | list of string | no | Keywords for search. |
| `home` | string | no | The URL of the project's home page. |
| `sources` | list of string | no | URLs of the source code for this chart or the software it deploys. |
| `dependencies` | list of [Dependency](#52-dependency-fields) | no | The charts this chart depends on. See [Section 5](#5-dependencies). |
| `maintainers` | list of [Maintainer](#45-maintainers) | no | The people who maintain the chart. |
| `icon` | string | no | The URL of an SVG or PNG image to use as the chart icon. |
| `appVersion` | string | no | The version of the application the chart deploys. It does not need to be SemVer. |
| `deprecated` | boolean | no | `true` if the chart is deprecated. Default `false`. |
| `annotations` | map of string to string | no | Extra metadata. See [Section 4.8](#48-annotations). |
| `condition` | string | no | **Legacy, unused.** Kept for compatibility. Implementations MUST NOT give it meaning. Conditions belong on a dependency entry. |
| `tags` | string | no | **Legacy, unused.** Kept for compatibility. Implementations MUST NOT give it meaning. Tags belong on a dependency entry. |

Field names are case-sensitive.

**Unknown fields.** The reference implementation ignores unknown top-level
fields when it loads a chart. `helm lint` reports them as a warning. The
documentation says extra fields are not allowed. Charts SHOULD NOT have
unknown fields. Implementations that load charts SHOULD accept and ignore
unknown fields. Implementations that write `Chart.yaml` MUST NOT drop unknown
fields without telling the user. Note that `helm package` re-serializes
`Chart.yaml` from the parsed model, so it drops unknown fields (see
[Section 14.3](#143-writing-an-archive)).

*Observed practice:* Two surveyed charts still have the Helm 2 field
`engine: gotpl`. Helm ignores it.

**Value types.** `version` and `appVersion` MUST be YAML strings. An unquoted
YAML number, such as `version: 1.0` or `appVersion: 1.10`, is parsed as a
float. That can change the value (`1.10` becomes `1.1`). `helm lint` reports
non-string `version` and `appVersion` values as errors. Authors SHOULD quote
values that look like numbers, for example `appVersion: "1.10"`.

**String sanitization.** When Helm validates metadata, it changes these
strings: `name`, `description`, `home`, `icon`, `condition`, `tags`,
`appVersion`, `kubeVersion`, each `sources` and `keywords` item, each
maintainer's `name`, `email`, and `url`, and each dependency's `name`,
`version`, `repository`, `condition`, and `tags` items. Every Unicode
whitespace character becomes an ASCII space (U+0020), and every non-printable
character is removed. Implementations that compare or show metadata SHOULD
apply the same change.

### 4.3 `name`

* MUST NOT be empty.
* MUST NOT be `.` or `..`.
* MUST NOT contain a path separator. Formally, it must equal its own
  `filepath.Base`, so `/` is not allowed (and `\` is not allowed on Windows).
* `helm create` also requires names to match `^[a-zA-Z0-9._-]+$` and to be at
  most 250 characters long.
* Chart names SHOULD use lowercase letters, digits, and dashes (`-`), start
  with a letter, and be at most 63 characters long. This lets the name be used
  in Kubernetes object names and labels. Uppercase letters, underscores, and
  dots SHOULD NOT be used.

The name of the chart directory SHOULD match `name`. A packaged chart's file
name is `<name>-<version>.tgz`.

*Observed practice:* All 190 surveyed charts use names that match
`^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`.

### 4.4 `version`

* MUST NOT be empty.
* MUST be a valid [SemVer 2](https://semver.org/spec/v2.0.0.html) version,
  for example `1.2.3`, `1.2.3-rc.1`, or `1.2.3+build.5`.
* Helm parses versions with Masterminds semver in non-strict mode. That mode
  also accepts a leading `v` and missing minor or patch numbers (`v1.2`,
  `1`). `helm lint` warns about these forms. Charts SHOULD use strict SemVer 2
  without a `v` prefix.
* `helm lint` reports an error if the version is not greater than `0.0.0-0`.
  For example, `0.0.0` itself is accepted, but a version below every
  pre-release of `0.0.0` is not.
* Build metadata (`+...`) is allowed. Some systems do not allow `+`. OCI tags
  replace `+` with `_`, and labels that contain the chart version replace it
  in the same way (see [Section 17.2](#172-standard-labels)).

Each new release of a chart's contents MUST have a new `version`. Chart
repositories and registries treat `name` plus `version` as an immutable
identity.

### 4.5 `maintainers`

Each item is a map:

| Field | Type | Required | Description |
|---|---|---|---|
| `name` | string | yes (lint) | The maintainer's name. |
| `email` | string | no | An email address. If present, `helm lint` requires a valid email address. |
| `url` | string | no | A URL. If present, `helm lint` requires a valid URL. |

The list MUST NOT contain null items. `helm lint` reports an error if `name`
is empty.

### 4.6 `kubeVersion`

`kubeVersion` is a Masterminds semver range (see [Section 5.3](#53-version-ranges)),
for example `>= 1.25.0-0` or `^1.28.0-0`. When it is set, install, upgrade,
and template operations MUST fail if the target Kubernetes version does not
satisfy the range. The error is `chart requires kubeVersion: <range> which is
incompatible with Kubernetes <version>`.

Managed Kubernetes services often report versions with a pre-release suffix,
for example `v1.29.4-eks-036c24b`. Under SemVer rules, a pre-release version
only matches a range that has a pre-release part. Authors SHOULD add `-0` to
the lower bound (`>=1.25.0-0`) so these versions match.

*Observed practice:* 21 of 190 surveyed charts set `kubeVersion`. Almost all
of them use the `-0` suffix.

### 4.7 `type`

| Value | Meaning |
|---|---|
| missing, empty, or `application` | An application chart. It can be installed. |
| `library` | A library chart. See [Section 9.9](#99-library-charts). |

Any other value MUST be rejected. Validation compares the value
case-sensitively. However, the check "is this a library chart?" in the
reference implementation ignores case. Charts MUST use lowercase values.

`helm install` MUST refuse to install a chart whose `type` is not empty or
`application`. The error is `<type> charts are not installable`.

### 4.8 `annotations`

`annotations` is a map from strings to strings. Values MUST be strings.
Structured data, such as YAML lists, MUST be written as a string that
contains YAML, usually with a `|` block scalar. Helm gives no meaning to any
annotation key. Other tools in the ecosystem use them.

*Observed practice:* These keys are widely used:

| Key | Used by | Meaning |
|---|---|---|
| `artifacthub.io/changes` | Artifact Hub | A YAML list of changes, as a string. |
| `artifacthub.io/links` | Artifact Hub | A YAML list of `{name, url}`, as a string. |
| `artifacthub.io/license` | Artifact Hub | An SPDX license ID. |
| `artifacthub.io/signKey` | Artifact Hub | The fingerprint and URL of the provenance signing key. |
| `artifacthub.io/maintainers`, `artifacthub.io/operator`, `artifacthub.io/prerelease`, `artifacthub.io/category`, `artifacthub.io/images`, `artifacthub.io/containsSecurityUpdates`, `artifacthub.io/crds` | Artifact Hub | See the Artifact Hub documentation. |
| `images` | Bitnami | A YAML list of the container images the chart uses. |
| `licenses` | Bitnami | An SPDX license expression. |
| `category`, `tanzuCategory` | Bitnami / VMware | A catalog category. |

Tools SHOULD use a namespaced key, such as `example.com/key`, for their own
annotations.

## 5. Dependencies

### 5.1 Overview

A chart can depend on other charts. In `v2`, dependencies are declared in the
`dependencies` list in `Chart.yaml`. (In `v1` they were in `requirements.yaml`.)
The dependency charts themselves live in `charts/`.

There are two ways to fill `charts/`:

1. **Managed.** Declare the dependency in `Chart.yaml` with a `repository`,
   then run `helm dependency update`. This resolves version ranges, writes
   `Chart.lock`, and downloads `<name>-<version>.tgz` archives into `charts/`.
   `helm dependency build` downloads the exact versions in an existing
   `Chart.lock`.
2. **Manual.** Copy a chart directory or archive into `charts/`.

Before install, upgrade, or template, the reference implementation checks
that every dependency declared in `Chart.yaml` is in `charts/`. The match uses
the chart name. If one is missing, the operation fails with `found in
Chart.yaml, but missing in charts/ directory: <names>`. Charts in `charts/`
that are not declared are still used. `helm lint` reports them as errors.

### 5.2 Dependency Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `name` | string | **yes** | The name of the dependency chart. MUST equal the `name` in that chart's `Chart.yaml`. |
| `version` | string | yes, for managed dependencies | A SemVer version or range ([Section 5.3](#53-version-ranges)). |
| `repository` | string | yes, for managed dependencies | Where to get the chart ([Section 5.4](#54-repository)). |
| `condition` | string | no | Comma-separated paths to booleans in the values. See [Section 5.6](#56-conditions-and-tags). |
| `tags` | list of string | no | Tags that enable or disable the dependency. See [Section 5.6](#56-conditions-and-tags). |
| `import-values` | list | no | Values to copy from the child into the parent. See [Section 5.7](#57-import-values). |
| `alias` | string | no | Another name for the dependency. See [Section 5.5](#55-alias). |

Implementations MUST NOT treat `enabled` as a user setting. It exists only in
memory, where it holds the result of the condition and tag rules. Charts
SHOULD NOT set it.

Rules:

* A dependency entry MUST NOT be null.
* `alias`, if set, MUST match `^[a-zA-Z0-9_-]+$`.
* For each dependency, take `alias` if it is set, otherwise `name`. These
  keys MUST be unique within one `Chart.yaml`.

### 5.3 Version Ranges

`version` uses the
[Masterminds semver constraint syntax](https://github.com/Masterminds/semver#checking-version-constraints):

| Syntax | Meaning |
|---|---|
| `1.2.3` or `=1.2.3` | Exactly this version. |
| `!=1.2.3` | Any version except this one. |
| `>`, `>=`, `<`, `<=` | Comparisons, for example `>=1.2.0`. |
| `>=1.2.0 <2.0.0` or `>=1.2.0, <2.0.0` | Space or comma means AND. |
| `\|\|` | OR, for example `^1.0.0 \|\| ^2.0.0`. |
| `1.2.x`, `1.x`, `*` | Wildcards. |
| `~1.2.3` | Patch-level changes: `>=1.2.3 <1.3.0`. |
| `^1.2.3` | Changes that do not modify the left-most non-zero part: `>=1.2.3 <2.0.0`. For `^0.2.3`, `>=0.2.3 <0.3.0`. |
| `1.2 - 1.4.5` | Hyphen range: `>=1.2 <=1.4.5`. |

Pre-release versions match only when the range has a pre-release part (for
example `^1.2.3-0`). When a range is resolved, the highest version in the
repository that matches is chosen.

*Observed practice:* Bitnami charts use wildcard ranges (`2.x.x`). Other
publishers mostly pin exact versions or use `~`, `^`, or `>=` ranges.

### 5.4 `repository`

| Form | Example | Meaning |
|---|---|---|
| HTTP(S) chart repository URL | `https://charts.example.com/stable` | A classic chart repository. The client reads `<url>/index.yaml`. |
| OCI registry reference | `oci://registry.example.com/charts` | An OCI registry. The chart is at `<repository>/<name>:<version>`. |
| Local path | `file://../common` | A chart directory on the local disk. A relative path is relative to the chart root of the chart that declares it. |
| Repository name | `@stable` or `alias:stable` | A repository name the user added with `helm repo add`. It only works on machines with that configuration, so it is NOT RECOMMENDED for published charts. |
| empty | | The dependency MUST already be in `charts/`. |

*Observed practice:* Of 223 dependency entries in the surveyed charts, 193
use `oci://`, 24 use `https://`, 1 uses `file://`, and 5 have no repository.

### 5.5 Alias

`alias` gives a dependency a different name inside the parent. A chart can
use the same dependency more than once by giving each copy a different alias:

```yaml
dependencies:
  - name: redis
    version: "^19.0.0"
    repository: oci://registry-1.docker.io/bitnamicharts
    alias: cache
  - name: redis
    version: "^19.0.0"
    repository: oci://registry-1.docker.io/bitnamicharts
    alias: queue
```

When a dependency has an alias, the implementation MUST use a copy of the
subchart whose metadata `name` is the alias. The alias is then used for:

* the key of the subchart's values in the parent (`.Values.cache`),
* `.Chart.Name` inside the subchart,
* the path in template names (`parent/charts/cache/templates/...`).

To pick the chart for an alias, the implementation looks for a subchart in
`charts/` whose `name` equals the dependency `name`. If the dependency has a
`version`, the subchart's version MUST also satisfy it.

A subchart in `charts/` that matches no dependency entry stays in the chart
under its own name.

### 5.6 Conditions and Tags

Conditions and tags decide whether a dependency is enabled. The
implementation evaluates them against the merged values (the chart defaults
plus user values, see [Section 7](#7-values)) before it renders templates.

**Tags.** A dependency's `tags` list is matched against the top-level `tags`
map in the parent's values:

```yaml
# values.yaml of the top-level chart
tags:
  front-end: false
  back-end: true
```

* If the dependency has no tags, or none of its tags is in the `tags` map,
  tags do not affect it.
* If **any** of its tags is `true`, the tags enable it.
* Otherwise, if the tags that are present are all `false`, the tags disable
  it.

**Conditions.** `condition` is a comma-separated list of value paths in dot
notation, for example `subchart1.enabled,global.subchart1.enabled`. The
implementation looks up the paths in order. The **first** path that resolves
to a boolean decides whether the dependency is enabled. Paths that do not
exist are skipped. If a path exists but its value is not a boolean, the
implementation SHOULD warn and skip it. If no path resolves, the condition
does not affect the dependency.

**Precedence.** If a condition resolves, it overrides tags. If no condition
resolves, the tag result applies. If neither applies, the dependency is
enabled.

**Scope.** For a dependency of a nested chart, paths are resolved relative to
that chart's values. For example, for a dependency of the subchart `sub`,
`foo.enabled` resolves as `sub.foo.enabled` in the top-level values. Tags are
always read from the top-level `tags` map.

Disabled dependencies are removed before rendering. Their templates are not
rendered and their values are not used. The implementation evaluates nested
dependencies recursively.

*Observed practice:* The most common condition form is
`<dependency-name>.enabled`. 105 of 223 surveyed dependency entries set a
condition. Bitnami charts tag their `common` library chart with
`bitnami-common`.

### 5.7 Import Values

`import-values` copies values from an enabled child chart into the parent
chart's values. Each item is in one of two forms:

1. **String form.** `- data` copies the child's `exports.data` map into the
   root of the parent's values. The child must have a top-level `exports`
   key in its values:

   ```yaml
   # child values.yaml
   exports:
     data:
       myint: 99
   # parent Chart.yaml
   dependencies:
     - name: child
       import-values:
         - data
   # result in parent: myint: 99
   ```

2. **Map form.** `{child: <path>, parent: <path>}` copies the value at the
   child path to the parent path. Paths use dot notation. A `parent` value of
   `.` means the root of the parent's values.

   ```yaml
   import-values:
     - child: default.data
       parent: myimports
   ```

Rules:

* Imported values have lower priority than the parent's own values. If the
  parent's `values.yaml` or the user's values already set a key, the
  imported value does not replace it. Maps are merged.
* Imports are done from the deepest charts up, so a grandchild's values can
  be imported into a child and then into the parent.
* Only enabled dependencies are imported.

*Observed practice:* None of the 190 surveyed charts use `import-values`.
Tools MUST still support it.

## 6. Chart.lock

`Chart.lock` records the exact versions that `helm dependency update` chose
for the ranges in `Chart.yaml`. It is OPTIONAL. If it is present, `helm
dependency build` uses it to download exactly the same versions.

```yaml
dependencies:
- name: common
  repository: oci://registry-1.docker.io/bitnamicharts
  version: 2.31.4
digest: sha256:90bb914faa525f3b5b11f8a5eaa39a47ee3f3117f9330d0babc78a03001a1663
generated: "2025-08-18T16:50:21.811944+02:00"
```

| Field | Type | Description |
|---|---|---|
| `generated` | string (RFC 3339 timestamp) | When the lock file was created. |
| `digest` | string | `sha256:` followed by a lowercase hex SHA-256 digest. See below. |
| `dependencies` | list | One entry for each resolved dependency, with `name`, `repository`, and exact `version`. |

**Digest algorithm.** The reference implementation computes the digest like
this:

1. Take the `dependencies` list from `Chart.yaml`. Replace each
   repository-name form (`@name`, `alias:name`) with the URL of that
   repository. This step depends on the client's configuration.
2. Take the list of locked dependencies.
3. Build a JSON array with two items: `[<Chart.yaml dependencies>, <locked
   dependencies>]`. Encode each dependency as a JSON object with keys in this
   order: `name`, `version`, `repository`, `condition`, `tags`, `enabled`,
   `import-values`, `alias`. Leave out `version`, `condition`, `tags`,
   `enabled`, `import-values`, and `alias` when they are empty. Always
   include `name` and `repository`. Use Go `encoding/json` rules (no extra
   whitespace, and `<`, `>`, `&` are escaped as `\u003c`, `\u003e`, `\u0026`).
4. Compute SHA-256 of these bytes and write it as `sha256:<hex>`.

`helm dependency build` MUST fail if the digest does not match. The error
says the lock file is out of sync with `Chart.yaml`. Tools that change
`dependencies` in `Chart.yaml` SHOULD regenerate `Chart.lock` (for example
with `helm dependency update`) or tell the user to do it. Because of step 1,
tools that do not reproduce Helm's repository configuration SHOULD treat the
digest as an opaque value.

*Observed practice:* 118 of 190 surveyed charts commit `Chart.lock`.

## 7. Values

### 7.1 `values.yaml`

`values.yaml` holds the chart's default values. It is OPTIONAL. If it is
present, it MUST be YAML whose top level is a map. Rules:

* The file MAY have more than one YAML document (separated by `---`). The
  implementation MUST merge the documents in order. Later documents override
  earlier ones, maps are merged recursively, and other values are replaced.
* An empty file, or a file with only comments, means no values (`{}`).
* Keys are case-sensitive. Values can be any YAML type: map, list, string,
  number, boolean, or null.
* Some keys are reserved. They have a special meaning when they are at the
  top level:

| Key | Meaning |
|---|---|
| `global` | Values copied to the chart and all its subcharts ([Section 7.4](#74-global-values)). |
| `tags` | Enables or disables dependencies by tag ([Section 5.6](#56-conditions-and-tags)). Read only from the top-level chart's values. |
| `<subchart name or alias>` | Values for that subchart ([Section 7.3](#73-subchart-values)). |
| `exports` | Values a child offers for `import-values` ([Section 5.7](#57-import-values)). |

Authors SHOULD use camelCase keys that start with a lowercase letter, and
SHOULD document each key with a comment.

### 7.2 Merging Values (Coalescing)

The values a template sees come from these sources, from lowest to highest
priority:

1. The chart's `values.yaml`.
2. For a subchart: the parent chart's values under the subchart's key. The
   parent's values override the subchart's defaults.
3. Values imported with `import-values` (lower priority than the importing
   chart's own values, see [Section 5.7](#57-import-values)).
4. User-supplied values: values files (`-f`), applied in order, and then
   `--set`-style flags. Each later source overrides the earlier ones.

The implementation merges two value trees, *higher* over *lower*, like this:

* If a key is only in *lower*, copy it.
* If both values are maps, merge them recursively.
* Otherwise, the *higher* value replaces the *lower* value. **Lists are never
  merged. They are replaced.**
* If one value is a map and the other is not, the *higher* value wins. The
  implementation SHOULD warn (Helm prints `skipped value for <key>: Not a
  table`).
* **Null removes a key.** If a user-supplied value is `null`, the key is
  removed from the result, even if the chart's defaults set it. Users can use
  this to remove a default. A `null` in a chart's own `values.yaml` does not
  appear in the result.

*Implementation quirk:* in the reference implementation, a `null` that a
parent chart sets for a subchart key (for example `sub: {key: null}` in the
parent's `values.yaml`) removes the subchart's default only if the user also
supplies values for that subchart. Charts SHOULD NOT depend on this. Tools
SHOULD document which behavior they use.

### 7.3 Subchart Values

A subchart reads its values from the parent's values under a key equal to the
subchart's name, or its alias if it has one:

```yaml
# parent values.yaml
mysql:            # values for the subchart named "mysql"
  auth:
    database: app
```

Inside the subchart, `.Values` is that subtree merged over the subchart's own
`values.yaml`. A subchart cannot read its parent's values, except for
`global`. If the parent sets the subchart's key to something that is not a
map, the subchart's defaults are used and the implementation SHOULD warn.

### 7.4 Global Values

The top-level key `global` is copied from each chart to all its subcharts:

* Inside every chart, `.Values.global` is the parent's `global` merged over
  the chart's own `global`. **The parent's values win.**
* Maps inside `global` are merged recursively.
* Globals only go down. A subchart cannot change its parent's globals.

### 7.5 Values Available at Render Time

After merging, dependency processing ([Section 5.6](#56-conditions-and-tags),
[Section 5.7](#57-import-values)), and schema validation
([Section 8](#8-valuesschemajson)), the full value tree is ready. Each
template sees its own chart's part of it as `.Values`.

## 8. values.schema.json

`values.schema.json` is OPTIONAL. It is a [JSON Schema](https://json-schema.org/)
document that describes the chart's values.

* It MUST be valid JSON. `helm package` fails if it is not.
* The implementation validates the **final merged values** of the chart
  ([Section 7.2](#72-merging-values-coalescing)) against the schema. It does
  not validate `values.yaml` alone.
* The implementation validates each subchart's schema against that
  subchart's part of the values. It only does this if the part exists and is
  not null. Disabled dependencies have been removed by then, so they are not
  validated.
* `helm install`, `helm upgrade`, `helm template`, and `helm lint` validate the
  schema. Users can turn validation off (`--skip-schema-validation`). If
  validation fails, the operation MUST fail and report which charts failed.
* Supported drafts: draft-04, draft-06, draft-07, 2019-09, and 2020-12, chosen
  by `$schema`. If `$schema` is missing or is `http://json-schema.org/schema#`,
  draft 2020-12 is used.
* `format` is an annotation only. It is not checked.
* `$ref` can load `file://`, `http://`, and `https://` URLs (HTTP has a
  15-second timeout), and `urn:` identifiers. A `urn:` reference that cannot
  be resolved is replaced by a schema that allows anything, and the
  implementation SHOULD warn. Schemas that load remote references make
  rendering depend on the network. Charts SHOULD NOT use them.
* YAML values are converted to JSON types before validation. Integers become
  numbers, and map keys must be strings.

*Observed practice:* 37 of 190 surveyed charts have a schema. The most common
`$schema` is `http://json-schema.org/schema#` (22). Others use draft-07 (6),
2019-09 (1), and 2020-12 (3). Tools such as `helm-schema` and
`helm-values-schema-json` generate schemas from annotated `values.yaml` files.

## 9. Templates

### 9.1 Template Files

Every file under `templates/` is a template. The engine treats files
differently based on the **base name**:

| Base name | Treatment |
|---|---|
| Starts with `_` (for example `_helpers.tpl`) | A *partial*. It is parsed, so its `define` blocks can be used, but it is not rendered as output. |
| `NOTES.txt` | Rendered. The output is shown to the user after install or upgrade. It is not a manifest ([Section 9.7](#97-notestxt)). |
| Anything else | Rendered. The output is a stream of Kubernetes manifests. |

`helm lint` reports an error for any file under `templates/` whose extension
is not `.yaml`, `.yml`, `.tpl`, or `.txt`. The extension does not change how
a file is rendered. For example, a `templates/helpers.tpl` file without the
leading `_` is rendered as manifests. Authors SHOULD use:

* `.yaml` for templates that produce manifests,
* `.tpl` and a leading `_` for files that only have `define` blocks,
* `.txt` only for `NOTES.txt`.

Files in `templates/` whose names start with `.` are excluded by the default
`.helmignore` rule `templates/.?*`, which Helm always adds when it loads a
chart from a directory ([Section 13](#13-helmignore)).

*Observed practice:* In the survey, template files were `.yaml` (4164),
`.tpl` (260), `.txt` (178), and `.yml` (17).

### 9.2 Template Language

Templates use the Go [`text/template`](https://pkg.go.dev/text/template)
language. Helm adds the function library described in
[Section 9.5](#95-functions).

* Delimiters are `{{` and `}}`. `{{-` and `-}}` remove the whitespace next to
  them.
* Missing map keys render as the zero value. The text `<no value>` is removed
  from the output. If the engine's `Strict` option is set (a library option;
  `helm lint --strict` does not set it), a missing key is an error.
* Each template is rendered with a data object (the *dot*) described in
  [Section 9.3](#93-built-in-objects).

**Template names.** Each template is named by its chart path:
`<chart>/templates/<file>` for the top-level chart, and
`<chart>/charts/<subchart>/templates/<file>` for subcharts, at any depth. The
alias is used when a subchart has one.

**One shared namespace.** All templates of a chart and all its subcharts are
parsed into one Go template set. So a named template (`{{ define "x" }}`) is
**global**: every chart in the tree can see it. If two charts define the same
name, the one parsed last wins. Templates are parsed in this order: paths
with more `/` separators first (deepest subcharts), and paths with the same
depth in reverse alphabetical order. As a result, a parent chart's
definitions override its subcharts' definitions. Authors MUST prefix the
names they define with the chart name, for example `{{ define
"mychart.fullname" }}`.

**Output.** The output of each template is split into YAML documents with
the regular expression `(?m)^---[ \t]*`. Documents that are empty or only
whitespace are dropped. Each document SHOULD be one Kubernetes object.
Rendered output MUST be valid YAML.

### 9.3 Built-in Objects

Every template's dot has these top-level keys:

| Object | Description |
|---|---|
| `.Values` | The chart's merged values ([Section 7](#7-values)). |
| `.Chart` | The chart's `Chart.yaml` metadata, with **Go field names** (see below). |
| `.Release` | Information about the release. |
| `.Capabilities` | Information about the Kubernetes cluster and the Helm client. |
| `.Template` | Information about the current template. |
| `.Files` | The chart's ordinary files ([Section 9.4](#94-accessing-files)). |
| `.Subcharts` | The render context (dot) of each subchart, keyed by subchart name (or alias). For example, `.Subcharts.mysql.Values`. |

**`.Chart`** uses the Go struct field names, not the YAML keys:

| Template field | `Chart.yaml` key |
|---|---|
| `.Chart.Name` | `name` (the alias, for an aliased subchart) |
| `.Chart.Version` | `version` |
| `.Chart.AppVersion` | `appVersion` |
| `.Chart.APIVersion` | `apiVersion` |
| `.Chart.Description` | `description` |
| `.Chart.Type` | `type` |
| `.Chart.KubeVersion` | `kubeVersion` |
| `.Chart.Home`, `.Chart.Icon` | `home`, `icon` |
| `.Chart.Sources`, `.Chart.Keywords` | `sources`, `keywords` |
| `.Chart.Maintainers` | `maintainers` (each item has `.Name`, `.Email`, `.URL`) |
| `.Chart.Annotations` | `annotations` |
| `.Chart.Deprecated` | `deprecated` |
| `.Chart.Dependencies` | `dependencies` (each item has `.Name`, `.Version`, `.Repository`, `.Condition`, `.Tags`, `.Enabled`, `.ImportValues`, `.Alias`) |
| `.Chart.Condition`, `.Chart.Tags` | the legacy `condition` and `tags` fields |
| `.Chart.IsRoot` | Computed. `true` for the top-level chart. |

**`.Release`**:

| Field | Description |
|---|---|
| `.Release.Name` | The release name. |
| `.Release.Namespace` | The namespace the release is installed in. |
| `.Release.IsInstall` | `true` for an install. |
| `.Release.IsUpgrade` | `true` for an upgrade. |
| `.Release.Revision` | The revision number. It is 1 on install and goes up by one on each new revision. A rollback reuses the stored manifests and does not render templates again. |
| `.Release.Service` | Always `"Helm"`. |

**`.Capabilities`**:

| Field | Description |
|---|---|
| `.Capabilities.KubeVersion.Version` | The Kubernetes version, for example `v1.31.2`. |
| `.Capabilities.KubeVersion.Major`, `.Minor` | The major and minor versions as strings. |
| `.Capabilities.KubeVersion` | Also renders as the version string. |
| `.Capabilities.APIVersions` | The API group versions and resources the cluster offers. |
| `.Capabilities.APIVersions.Has "<group/version>"` | `true` if the API is available. Also accepts `"<group/version>/<Kind>"`. |
| `.Capabilities.HelmVersion` | `.Version`, `.GitCommit`, `.GitTreeState`, `.GoVersion`, and `.KubeClientVersion` of the Helm client. |

When there is no cluster, for example in `helm template` or `helm lint`,
`.Capabilities` holds default values. The Kubernetes version comes from the
version of the Kubernetes client library that Helm was built with, and
`APIVersions` lists the built-in Kubernetes APIs. Users can change these with
`--kube-version` and `--api-versions`.

**`.Template`**:

| Field | Description |
|---|---|
| `.Template.Name` | The template's name, for example `mychart/templates/deployment.yaml`. |
| `.Template.BasePath` | The chart's templates directory, for example `mychart/templates`. |

### 9.4 Accessing Files

`.Files` gives access to the chart's ordinary files: every file that is not
`Chart.yaml`, `Chart.lock`, `values.yaml`, `values.schema.json`, under
`templates/`, or a subchart ([Section 3.2](#32-reserved-paths)). Files left
out by `.helmignore` are not available.

| Function | Returns |
|---|---|
| `.Files.Get "path"` | The file's content as a string, or `""` if the file does not exist. |
| `.Files.GetBytes "path"` | The file's content as bytes. |
| `.Files.Glob "pattern"` | A new `Files` object with the matching files. The pattern uses [gobwas/glob](https://github.com/gobwas/glob) syntax with `/` as the separator, so `**` matches across directories. |
| `.Files.Lines "path"` | The file split into lines. |
| `.Files.AsConfig` | The files as a YAML map from base name to content, for a ConfigMap `data` field. |
| `.Files.AsSecrets` | The files as a YAML map from base name to base64 content, for a Secret `data` field. |

Paths are relative to the chart root and use `/`. Templates of a chart cannot
read the files of another chart (parent or subchart).

### 9.5 Functions

Templates can use:

1. The Go `text/template` built-ins: `and`, `or`, `not`, `eq`, `ne`, `lt`,
   `le`, `gt`, `ge`, `len`, `index`, `slice`, `print`, `printf`, `println`,
   `html`, `js`, `urlquery`, and `call`.
2. The [Sprig](https://masterminds.github.io/sprig/) v3 library, **without**
   `env` and `expandenv`. These are removed so that rendering does not depend
   on the machine it runs on.
3. These functions that Helm adds:

| Function | Description |
|---|---|
| `include NAME DATA` | Renders the named template and returns a string. Unlike `template`, the result can be piped. Calls can be nested up to 1000 levels (recursion limit). |
| `tpl STRING DATA` | Renders a string as a template, using the given data. |
| `required MSG VALUE` | Fails rendering with MSG if VALUE is nil or an empty string. |
| `fail MSG` | Fails rendering with MSG. |
| `lookup APIVERSION KIND NAMESPACE NAME` | Reads live objects from the cluster. Returns an empty map if there is no cluster (`helm template`, `helm lint`, `--dry-run` without server access). If NAME is empty, it returns a list object. |
| `toYaml`, `mustToYaml`, `toYamlPretty`, `fromYaml`, `fromYamlArray` | YAML encoding and decoding. `fromYaml` returns a map with an `Error` key if parsing fails, and `mustToYaml` fails rendering instead. |
| `toJson`, `mustToJson`, `fromJson`, `fromJsonArray` | JSON encoding and decoding. |
| `toToml`, `mustToToml`, `fromToml` | TOML encoding and decoding. |
| `mustToDuration`, `durationSeconds`, `durationMilliseconds`, `durationMicroseconds`, `durationNanoseconds`, `durationMinutes`, `durationHours`, `durationDays`, `durationWeeks`, `durationRoundTo`, `durationTruncateTo` | Duration helpers. Added in Helm 4. |
| `getHostByName NAME` | Looks up a host's IP address. Returns `""` unless DNS lookups are turned on (`--enable-dns`). |

Charts that must work with older Helm 3 clients SHOULD NOT use the duration
helpers, and SHOULD check which functions those clients have.

### 9.6 Partials and Named Templates

Named templates are made with `{{ define "name" }} ... {{ end }}` and used with
`include` (RECOMMENDED) or `template`. By convention they are kept in files
whose names start with `_`, such as `templates/_helpers.tpl`. As explained in
[Section 9.2](#92-template-language), names are global across the chart tree.

### 9.7 NOTES.txt

After rendering, every output whose name ends in `NOTES.txt` is removed from
the manifests. The output of the top-level chart's `templates/NOTES.txt` is
shown to the user after install and upgrade, and with `helm status`.
Subcharts' `NOTES.txt` files are only shown if the user asks for them
(`--render-subchart-notes`). If they are shown, all notes are joined with a
newline between them.

### 9.8 Rendering Pipeline (Summary)

An implementation that renders a chart the way Helm does MUST follow these
steps in order:

1. Load the chart and its subcharts ([Section 3](#3-chart-structure)).
2. Check that every dependency declared in `Chart.yaml` is in `charts/`.
3. Merge user values with the chart defaults, without the subchart
   defaults yet ([Section 7.2](#72-merging-values-coalescing)).
4. Process dependencies: resolve aliases, evaluate conditions and tags,
   remove disabled subcharts, and process `import-values`
   ([Section 5](#5-dependencies)).
5. Merge all values, including subchart defaults and globals.
6. Validate the values against each chart's `values.schema.json`
   ([Section 8](#8-valuesschemajson)).
7. If `kubeVersion` is set, check it ([Section 4.6](#46-kubeversion)).
8. Build the top-level objects and render all templates
   ([Section 9.2](#92-template-language) to [Section 9.5](#95-functions)).
9. Remove partials, empty output, and `NOTES.txt`. Split the output into
   documents.
10. Put each document with a valid `helm.sh/hook` annotation into the hooks.
    Put the rest into the manifests ([Section 11](#11-hooks-and-tests)).
11. Sort the manifests by kind ([Section 12.1](#121-install-order)).
12. Load the CRDs in `crds/` separately ([Section 10](#10-custom-resource-definitions-crds)).

### 9.9 Library Charts

A library chart (`type: library`) provides named templates for other charts
to use. It does not produce resources.

* Only files whose base name starts with `_` are used. Other templates in a
  library chart are ignored.
* A library chart MUST NOT be installed directly.
* To use a library chart, list it as a dependency. Its `define` blocks are
  then available to the parent chart, because the template namespace is
  shared.
* A library chart MAY have `values.yaml`. Its values are merged like any
  other subchart's values.

*Observed practice:* The Bitnami `common` chart is the most used library
chart. The surveyed Bitnami charts all depend on it, and it is the only
surveyed chart with `type: library`.

## 10. Custom Resource Definitions (crds/)

The `crds/` directory holds CustomResourceDefinition manifests that must
exist before the chart's templates are applied.

* Files in `crds/` (at any depth below it) whose extension is `.yaml`,
  `.yml`, or `.json` (in any letter case) are CRD files. Other files in
  `crds/` are ordinary files.
* CRD files are **not templated**. They are applied exactly as written. A
  file MAY have more than one YAML document separated by `---`.
* Each document MUST be a CustomResourceDefinition: `apiVersion` in the
  `apiextensions.k8s.io` group and `kind: CustomResourceDefinition`.
  `helm lint` reports other kinds as errors.
* CRDs are collected from the chart and from every **enabled** subchart,
  after dependency processing.
* On **install**, Helm creates the CRDs before it renders the templates. It
  then waits until they are established, so that `.Capabilities.APIVersions`
  includes them. CRDs that already exist are skipped. Users can skip this
  step with `--skip-crds`.
* On **upgrade** and **rollback**, Helm does not install or change CRDs. On
  **uninstall**, Helm does not delete them.
* `helm template` leaves CRDs out of its output unless `--include-crds` is
  set.

Charts that need to manage the CRD lifecycle (for example, to upgrade CRDs)
often put the CRDs in `templates/` instead, guarded by a value such as
`crds.install`. Then the CRDs are normal release resources and are upgraded
and deleted with the release. Authors SHOULD add
`helm.sh/resource-policy: keep` to such CRDs, so that uninstalling the chart
does not delete all custom resources of that type.

*Observed practice:* 25 of 190 surveyed charts have a `crds/` directory.
Several others template their CRDs behind values such as `crds.enabled` or
`crds.install`.

## 11. Hooks and Tests

### 11.1 Hook Annotation

A rendered manifest is a **hook** if its `metadata.annotations` has the key
`helm.sh/hook`. The value is a comma-separated list of events. Spaces around
each event are ignored, and the comparison ignores case.

| Event | When it runs |
|---|---|
| `pre-install` | After templates are rendered, before any resources are created. |
| `post-install` | After all resources are created (and ready, if waiting). |
| `pre-delete` | On uninstall, before any release resources are deleted. |
| `post-delete` | On uninstall, after all release resources are deleted. |
| `pre-upgrade` | On upgrade, after rendering, before any resources are updated. |
| `post-upgrade` | On upgrade, after all resources are updated. |
| `pre-rollback` | On rollback, after rendering, before any resources are rolled back. |
| `post-rollback` | On rollback, after all resources are rolled back. |
| `test` | When the user runs `helm test`. `test-success` is a legacy alias. |

Hook rules:

* If **any** event in the list is unknown, the whole manifest is dropped. It
  is not treated as a hook or as a normal resource. Implementations SHOULD
  warn about this.
* Hooks are not part of the release's normal resources. Helm does not track
  them for upgrades, and does not delete them on uninstall unless a delete
  policy applies.
* Hooks of the same event run one at a time. For a Job or Pod, Helm waits
  until it completes. Other kinds count as ready once Kubernetes has created
  them. If a hook fails, the operation fails.

| Annotation | Values | Default | Meaning |
|---|---|---|---|
| `helm.sh/hook-weight` | An integer as a string, for example `"-5"` | `0` (also used if the value is not a valid integer) | Order of execution. Lower weights run first. |
| `helm.sh/hook-delete-policy` | Comma-separated: `before-hook-creation`, `hook-succeeded`, `hook-failed` | `before-hook-creation` | When Helm deletes the hook resource. `before-hook-creation` deletes the previous resource before a new one is created. |
| `helm.sh/hook-output-log-policy` | Comma-separated: `hook-succeeded`, `hook-failed` | none | When Helm prints the logs of the hook's Pods, based on whether the hook succeeded or failed. |

**Hook order.** Hooks of one event are ordered by weight (ascending), then by
resource name (ascending). Kind order ([Section 12.1](#121-install-order)) is
only used to break ties.

Annotation values MUST be YAML strings. Numeric weights MUST be quoted
(`"5"`), because Kubernetes annotation values are strings.

### 11.2 Tests

A chart test is a hook with the `test` event, usually a Pod or a Job whose
container exits with status 0 on success. Tests run only when the user runs
`helm test <release>`. Tests SHOULD be in `templates/tests/`. The directory
has no special meaning to Helm; it is a convention.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: "{{ include "mychart.fullname" . }}-test-connection"
  annotations:
    "helm.sh/hook": test
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
spec:
  restartPolicy: Never
  containers:
    - name: wget
      image: busybox
      command: ["wget"]
      args: ["{{ include "mychart.fullname" . }}:{{ .Values.service.port }}"]
```

## 12. Resource Ordering and Special Annotations

### 12.1 Install Order

Helm sorts the normal manifests by `kind` before it applies them. Install
and upgrade use this order:

```text
PriorityClass, Namespace, NetworkPolicy, ResourceQuota, LimitRange,
PodSecurityPolicy, PodDisruptionBudget, ServiceAccount, Secret, SecretList,
ConfigMap, StorageClass, PersistentVolume, PersistentVolumeClaim,
CustomResourceDefinition, ClusterRole, ClusterRoleList, ClusterRoleBinding,
ClusterRoleBindingList, Role, RoleList, RoleBinding, RoleBindingList, Service,
DaemonSet, Pod, ReplicationController, ReplicaSet, Deployment,
HorizontalPodAutoscaler, StatefulSet, Job, CronJob, IngressClass, Ingress,
APIService, MutatingWebhookConfiguration, ValidatingWebhookConfiguration
```

* Kinds not in the list come after all listed kinds. Unlisted kinds are
  sorted alphabetically by kind.
* The sort is stable. Manifests of the same kind keep their order. That
  order is by template path (sorted as strings), then by position inside the
  file.
* Uninstall uses a different list, which is roughly the reverse.

Charts MUST NOT depend on any order other than this one. If a chart needs a
stricter order, it uses hooks with weights.

### 12.2 Annotations and Labels Helm Uses

| Key | Kind | Set by | Meaning |
|---|---|---|---|
| `helm.sh/hook`, `helm.sh/hook-weight`, `helm.sh/hook-delete-policy`, `helm.sh/hook-output-log-policy` | annotation | chart | See [Section 11](#11-hooks-and-tests). |
| `helm.sh/resource-policy: keep` | annotation | chart | Helm does not delete the resource on uninstall, or when an upgrade or rollback removes it from the chart. The resource stays in the cluster without an owner. `helm lint` reports an error if this annotation is on a `List`-kind object, because Helm cannot honor it there. |
| `meta.helm.sh/release-name`, `meta.helm.sh/release-namespace` | annotation | Helm | The release that owns the resource. Helm adds them to every resource it creates. |
| `app.kubernetes.io/managed-by: Helm` | label | Helm | Added together with the annotations above. |

Before Helm creates a resource, it checks whether one with the same kind,
name, and namespace already exists. If it does, it MUST have the ownership
annotations and label above with values that match the release. Otherwise
install or upgrade fails. Charts SHOULD NOT set these keys themselves.

## 13. .helmignore

`.helmignore` in the chart root lists files to leave out. Helm uses it
whenever it loads a chart **from a directory**: for `helm package`, `helm
install ./dir`, `helm template ./dir`, `helm lint`, and so on. It is not used
when loading an archive. The `.helmignore` file itself is not left out
unless it lists itself.

Syntax, one pattern per line:

* Leading and trailing whitespace is removed. Empty lines and lines that
  start with `#` are ignored. Comments at the end of a line are not
  supported.
* Patterns use Go [`filepath.Match`](https://pkg.go.dev/path/filepath#Match)
  syntax: `*`, `?`, `[...]`, and `\` to escape. `**` is **not supported**. A
  pattern that contains it makes loading fail.
* A pattern with no `/` is matched against the **base name** of each file and
  directory, at any depth.
* A pattern that starts with `/` is matched against the full path relative to
  the chart root.
* A pattern that contains `/` anywhere else is also matched against the full
  relative path.
* A pattern that ends with `/` only matches directories. If a directory
  matches, nothing inside it is loaded.
* A pattern that starts with `!` is **not** a gitignore-style exception.
  The reference implementation ignores every path that does **not** match a
  `!` pattern. So a `!` rule works like an allowlist, and it usually removes
  `Chart.yaml` too. Charts SHOULD NOT use `!` patterns.

Rules are checked in order, and the first rule that ignores a path wins.
Helm always adds the rule `templates/.?*` (dotfiles directly in `templates/`).

`.helmignore` only applies to the chart whose root it is in. When a parent
chart is loaded from a directory, files under `charts/<sub>/` are checked
against the **parent's** rules. The subchart's own `.helmignore` is just an
ordinary file. `helm dependency update` packages `file://` dependencies with
their own `.helmignore`.

`helm create` writes this default `.helmignore`:

```text
# Patterns to ignore when building packages.
# This supports shell glob matching, relative path matching, and
# negation (prefixed with !). Only one pattern per line.
.DS_Store
# Common VCS dirs
.git/
.gitignore
.bzr/
.bzrignore
.hg/
.hgignore
.svn/
# Common backup files
*.swp
*.bak
*.tmp
*.orig
*~
# Various IDEs
.project
.idea/
*.tmproj
.vscode/
```

## 14. Chart Archive (Package) Format

### 14.1 Format

A packaged chart is a gzip-compressed tar archive
([RFC 1952](https://www.rfc-editor.org/rfc/rfc1952) and POSIX `ustar`/PAX).

* The file name SHOULD be `<name>-<version>.tgz`, using the `name` and
  `version` from `Chart.yaml`.
* Every entry MUST be inside a single top-level directory. That directory
  SHOULD have the same name as the chart:

  ```text
  mychart-1.2.3.tgz
    mychart/Chart.yaml
    mychart/values.yaml
    mychart/templates/deployment.yaml
    mychart/charts/common/Chart.yaml
    ...
  ```

* Producers SHOULD write only regular file entries with mode `0644`.
  Directory entries are allowed but not needed.
* Producers SHOULD NOT write symlink, hard link, or device entries.

### 14.2 Reading an Archive

An implementation that reads chart archives MUST:

1. Decompress gzip. The data starts with the gzip magic bytes `1F 8B`. Helm
   checks for `1F 8B 08` (deflate) to tell an archive from other files.
2. Skip directory entries and PAX header entries (`x` and `g`).
3. Remove the **first path component** of every entry, whatever its name.
   Helm does not check that all entries have the same first component.
   Implementations SHOULD reject archives where they differ.
4. Treat `\` as a path separator if an entry name contains it, and convert
   it to `/`.
5. Reject the archive (do not just skip the entry) if, after step 3 and path
   cleaning, an entry:
   * is an absolute path,
   * is empty or `.` (content outside the top-level directory),
   * starts with `..` (it points outside the chart),
   * starts with a Windows drive letter (`^[a-zA-Z]:/`),
   * or if `Chart.yaml` is the archive's first path component (it is in the
     archive root instead of in a directory).
6. Limit the total decompressed size. Helm's default limit is **100 MiB**
   (`MaxDecompressedChartSize`), counted across all entries. Larger archives
   are rejected.
7. Strip a UTF-8 BOM from each file's content.
8. Reject an archive that has no file entries.

The resulting list of paths and contents is then sorted into categories as
described in [Section 3.2](#32-reserved-paths). Subchart `.tgz` files inside
`charts/` are read with the same rules, recursively.

These checks protect against path traversal ("zip slip") and decompression
bombs. Implementations MUST NOT write archive contents to disk without them.

### 14.3 Writing an Archive

`helm package` creates an archive like this. Other implementations SHOULD do
the same so that their archives work with Helm:

1. Load the chart from its directory, applying `.helmignore`.
2. Validate the metadata ([Section 16.1](#161-load-time-validation)).
3. Write the entries under `<name>/`:
   1. `Chart.yaml`, **serialized again from the parsed metadata**. Comments,
      key order, and unknown fields are lost, and keys are written in
      alphabetical order.
   2. `Chart.lock`, if present, also serialized again.
   3. `values.yaml`, byte for byte.
   4. `values.schema.json`, byte for byte. It MUST be valid JSON, or
      packaging fails.
   5. All templates, then all other files, byte for byte.
   6. Each subchart, written recursively under
      `<name>/charts/<subchart name>/`. Subchart archives (`.tgz`) in
      `charts/` are **expanded into directories** in the output.
4. Use file mode `0644` for every entry, and the file's modification time
   (or the current time if there is none).
5. Set the gzip header's comment to `Helm`. Helm also writes a fixed
   `Extra` field. It has no meaning.

`helm package` can also set `version` and `appVersion` from the command line
(`--version`, `--app-version`), and can update dependencies first
(`--dependency-update`).

Two packages built from the same source are not byte-identical unless the
modification times are the same.

### 14.4 Distribution

Charts are published to chart repositories (an `index.yaml` plus archives
over HTTP) or to OCI registries. These formats are out of scope here. In
short, for OCI:

| Item | Media type |
|---|---|
| Config | `application/vnd.cncf.helm.config.v1+json` (the `Chart.yaml` metadata as JSON) |
| Chart content layer | `application/vnd.cncf.helm.chart.content.v1.tar+gzip` (the archive described above) |
| Provenance layer | `application/vnd.cncf.helm.chart.provenance.v1.prov` |

OCI tags cannot contain `+`, so `+` in a chart version is replaced with `_`
in the tag.

## 15. Provenance

A chart archive can be signed. The signature is in a separate provenance
file with the name `<archive file name>.prov`, for example
`mychart-1.2.3.tgz.prov`.

A provenance file is an OpenPGP **clear-signed** message
([RFC 4880 section 7](https://www.rfc-editor.org/rfc/rfc4880#section-7)).
Helm uses SHA-512 as the signature hash. The signed text has two YAML
documents:

1. The chart's `Chart.yaml` metadata, serialized again.
2. After a line with only `...` (the YAML document end marker), a map of
   file checksums:

```text
-----BEGIN PGP SIGNED MESSAGE-----
Hash: SHA512

apiVersion: v2
appVersion: 1.16.0
description: A Helm chart for Kubernetes
name: mychart
type: application
version: 0.1.0

...
files:
  mychart-0.1.0.tgz: sha256:4d4a1d3f6e8a2b1c9e7f5a3b2c1d0e9f8a7b6c5d4e3f2a1b0c9d8e7f6a5b4c3d
-----BEGIN PGP SIGNATURE-----
...
-----END PGP SIGNATURE-----
```

To verify a chart, an implementation MUST:

1. Check the clear-signed signature against a trusted keyring.
2. Split the signed text at the first `\n...\n`. Parse the second part as
   YAML.
3. Check that `files` has an entry whose key is the archive's base file
   name, and whose value is `sha256:` followed by the lowercase hex SHA-256
   of the archive bytes.

The metadata part is for people to read. Helm does not use it to verify the
chart.

Provenance only covers the archive. It does not cover dependencies that are
downloaded later. Those have their own provenance files.

## 16. Validation and Linting

### 16.1 Load-Time Validation

An implementation that loads a chart MUST reject it if any of these are true.
These checks match `Metadata.Validate` in the reference implementation and run
on every load, install, template, and package.

1. `Chart.yaml` is missing or is not valid YAML.
2. `apiVersion` is empty after loading. (Helm sets a missing `apiVersion` to
   `v1` first, so in practice this cannot happen for Helm.)
3. `name` is empty, is `.` or `..`, or contains a path separator.
4. `version` is empty or cannot be parsed as a SemVer version (non-strict;
   see [Section 4.4](#44-version)).
5. `type` is not empty, `application`, or `library`.
6. `maintainers` contains a null item.
7. `dependencies` contains a null item, or an `alias` that does not match
   `^[a-zA-Z0-9_-]+$`.
8. Two dependencies have the same effective name (alias, or name if there
   is no alias).
9. `Chart.lock`, `values.yaml`, or `requirements.*` cannot be parsed.
10. A subchart in `charts/` fails any of these checks.
11. For archives: any rule in [Section 14.2](#142-reading-an-archive).

At install, upgrade, and template time, these checks are added:

* Every declared dependency is present in `charts/` ([Section 5.1](#51-overview)).
* `kubeVersion` matches the target cluster ([Section 4.6](#46-kubeversion)).
* The merged values match every `values.schema.json` ([Section 8](#8-valuesschemajson)).
* The chart is not a library chart ([Section 4.7](#47-type)).
* Templates render without errors, and each rendered document is valid YAML
  with `apiVersion`, `kind`, and `metadata.name` (the Kubernetes API server
  checks the rest).

### 16.2 Lint Rules

`helm lint` runs more checks. Each finding has a severity: **ERROR** (lint
fails), **WARNING** (lint fails only with `--strict`), or **INFO**.
Implementations that offer linting SHOULD include these rules and use the
same severities.

| Area | Rule | Severity |
|---|---|---|
| Chart.yaml | `Chart.yaml` is a directory, or cannot be parsed | ERROR |
| Chart.yaml | Unknown fields (strict parse fails) | WARNING |
| Chart.yaml | `name` is empty or contains a path separator | ERROR |
| Chart.yaml | `apiVersion` is empty, or not `v1` or `v2` | ERROR |
| Chart.yaml | `version` or `appVersion` is not a YAML string | ERROR |
| Chart.yaml | `version` is not valid SemVer, or not `> 0.0.0-0` | ERROR |
| Chart.yaml | `version` is not strict SemVer 2 (for example `v1.2.3` or `1.2`) | WARNING |
| Chart.yaml | Maintainer is null or has no `name`, or has an invalid `email` or `url` | ERROR |
| Chart.yaml | A `sources` item is empty or not a valid URL | ERROR |
| Chart.yaml | `icon` is missing | INFO |
| Chart.yaml | `icon` is not a valid URL | ERROR |
| Chart.yaml | `type` or `dependencies` used with `apiVersion: v1` | ERROR |
| values.yaml | The file is missing | INFO |
| values.yaml | Cannot be parsed, or the merged values fail the schema | ERROR |
| templates | `templates/` is missing | WARNING |
| templates | `templates` exists but is not a directory | ERROR |
| templates | The chart cannot be loaded, or rendering fails | ERROR |
| templates | A file's extension is not `.yaml`, `.yml`, `.tpl`, or `.txt` | ERROR |
| templates | A rendered YAML file starts with indentation | WARNING |
| templates | A rendered document is not valid YAML | ERROR |
| templates | `metadata.name` breaks the Kubernetes naming rules for that kind | WARNING |
| templates | The object uses a deprecated or removed Kubernetes API (for the target `--kube-version`) | WARNING |
| templates | A workload's `spec.selector` has neither `matchLabels` nor `matchExpressions` | ERROR |
| templates | A `List` object has `helm.sh/resource-policy` | ERROR |
| dependencies | A chart in `charts/` is not declared in `Chart.yaml` | ERROR |
| dependencies | Two dependencies have the same name or alias | ERROR |
| dependencies | A declared dependency is missing from `charts/` | WARNING |
| crds | `crds` exists but is not a directory | ERROR |
| crds | A CRD file is not valid YAML | ERROR |
| crds | A document's `apiVersion` is not in `apiextensions.k8s.io`, or `kind` is not `CustomResourceDefinition` | ERROR |

When `helm lint` renders templates:

* The release name is `test-release`.
* There is no cluster: `lookup` returns empty results, and `.Capabilities`
  has default values ([Section 9.3](#93-built-in-objects)).
* `required` and `fail` do **not** stop rendering. They are logged and return
  an empty string. This lets lint check charts that need values the user
  must supply.
* `import-values` is **not** processed.
* The values are the chart's `values.yaml` merged with any values the user
  passes to `helm lint`.

## 17. Conventions and Best Practices

This section is not normative unless it says otherwise. It summarizes the
Helm *Chart Best Practices Guide* and common practice in public charts.

### 17.1 General

* Chart names: lowercase letters, digits, and dashes ([Section 4.3](#43-name)).
* Versions: strict SemVer 2. Increase `version` for every change to the
  chart.
* YAML: indent with two spaces. Do not use tabs.
* Values: camelCase keys. Prefer maps over lists for things users will
  override, because lists are replaced as a whole ([Section 7.2](#72-merging-values-coalescing)).
  Comment every value. Quote strings that look like other types.
* Templates: one resource per file. Name files after the kind, in kebab
  case, such as `deployment.yaml` or `service-account.yaml`. Prefix the names
  of defined templates with the chart name. Do not set `metadata.namespace`
  in templates unless the chart really manages resources in more than one
  namespace. Helm sets the namespace when it applies resources.
* Use `include` with `nindent`/`indent` instead of `template`, so that the
  output can be indented.
* Images: let users set the registry, repository, tag (default:
  `.Chart.AppVersion`), digest, and pull policy.
* Document the chart in `README.md`. Many charts generate it from
  `values.yaml` comments with helm-docs (`README.md.gotmpl`).

### 17.2 Standard Labels

Charts SHOULD add these labels to every resource they create, and to the pod
templates of workloads:

| Label | Value | Notes |
|---|---|---|
| `app.kubernetes.io/name` | `{{ include "<chart>.name" . }}` | The app name. Use it in selectors. |
| `app.kubernetes.io/instance` | `{{ .Release.Name }}` | Separates releases. Use it in selectors. |
| `app.kubernetes.io/version` | `{{ .Chart.AppVersion }}` | Do not use it in selectors. |
| `app.kubernetes.io/managed-by` | `{{ .Release.Service }}` | Always `Helm`. |
| `helm.sh/chart` | `{{ .Chart.Name }}-{{ .Chart.Version \| replace "+" "_" }}` | Do not use it in selectors. `+` is not allowed in label values. |
| `app.kubernetes.io/component` | for example `server`, `worker` | OPTIONAL. |
| `app.kubernetes.io/part-of` | the larger application | OPTIONAL. |

Selector labels MUST NOT change between chart versions, because Kubernetes
does not allow changes to some selectors (for example on a Deployment).

### 17.3 Name Lengths

Kubernetes limits many names to 63 characters (DNS-1123 labels) or 253
characters (DNS-1123 subdomains). Helm limits release names to 53 characters
and requires them to match
`^[a-z0-9]([-a-z0-9]*[a-z0-9])?(\.[a-z0-9]([-a-z0-9]*[a-z0-9])?)*$`.
Templates that build names from the release name and chart name SHOULD
truncate them to 63 characters and remove a trailing `-`:

```gotemplate
{{- define "mychart.fullname" -}}
{{- if .Values.fullnameOverride -}}
{{- .Values.fullnameOverride | trunc 63 | trimSuffix "-" -}}
{{- else -}}
{{- $name := default .Chart.Name .Values.nameOverride -}}
{{- if contains $name .Release.Name -}}
{{- .Release.Name | trunc 63 | trimSuffix "-" -}}
{{- else -}}
{{- printf "%s-%s" .Release.Name $name | trunc 63 | trimSuffix "-" -}}
{{- end -}}
{{- end -}}
{{- end -}}
```

### 17.4 Starter Charts and `helm create`

`helm create <name>` makes a new `v2` application chart with:

* `Chart.yaml`: `apiVersion: v2`, `type: application`, `version: 0.1.0`,
  `appVersion: "1.16.0"`.
* `values.yaml` and the default `.helmignore` ([Section 13](#13-helmignore)).
* An empty `charts/` directory.
* `templates/`: `deployment.yaml`, `service.yaml`, `serviceaccount.yaml`,
  `hpa.yaml`, `ingress.yaml`, `httproute.yaml`, `NOTES.txt`, `_helpers.tpl`,
  and `tests/test-connection.yaml`.

`helm create --starter <starter>` copies a starter chart instead. Starter
charts are kept in Helm's data directory under `starters/`. When Helm copies
one, it replaces every `<CHARTNAME>` in the files with the new chart's name.
Starter charts SHOULD NOT be installed directly.

### 17.5 CI Values

*Observed practice:* Many charts keep values files for CI in `ci/`, for
example `ci/default-values.yaml` and `ci/ingress-values.yaml`. The
[chart-testing](https://github.com/helm/chart-testing) tool (`ct`) lints and
installs the chart once for each file that matches `ci/*-values.yaml`. Helm
itself gives `ci/` no meaning. Authors SHOULD list `ci/` in `.helmignore`.

## 18. Implementation Guidance for Tool Authors

This section collects advice for tools, including AI agents, that create or
change charts.

### 18.1 Reading Charts

* Read `apiVersion` first, and only use this specification for `v2`
  ([Section 4.1](#41-detecting-the-api-version)).
* Sort files into categories by path, as in [Section 3.2](#32-reserved-paths).
  Do not guess from file extensions.
* For archives, apply every safety check in [Section 14.2](#142-reading-an-archive).
* Expect both directory and `.tgz` subcharts in `charts/`.
* Do not assume that a subchart's directory name equals its chart name.
  Read its `Chart.yaml`.
* Parse YAML as YAML 1.1/1.2 compatible with Go. Be careful with
  unquoted values such as `yes`, `no`, `on`, `off`, and `1.10`.

### 18.2 Changing Charts

* Keep comments, key order, and formatting when you edit `Chart.yaml` and
  `values.yaml`. Use a YAML library that keeps comments, or edit the text.
  Do not re-serialize unless the user agrees.
* After you change `version`, check that it is still strict SemVer 2 and
  higher than the previous version.
* After you change `dependencies`, update `Chart.lock` and `charts/`
  (`helm dependency update`) or tell the user to do it
  ([Section 6](#6-chartlock)).
* After you change `values.yaml`, update `values.schema.json` (if there is
  one) and `README.md` (if it documents values).
* When you add a new named template, prefix its name with the chart name, so
  it does not clash with other charts ([Section 9.2](#92-template-language)).
* Do not add files to `charts/` that are not charts
  ([Section 3.3](#33-the-charts-directory)).
* Quote `version`, `appVersion`, and annotation values that look like
  numbers.

### 18.3 Rendering Charts

* Follow the pipeline in [Section 9.8](#98-rendering-pipeline-summary). Keep
  this order: conditions and tags are evaluated against merged values,
  before schema validation and rendering.
* Use Go `text/template` and the same Sprig version as Helm if you need
  identical output. Other template engines will differ in small ways, for
  example in whitespace, `printf` formatting, and map key order.
* Put all templates of the chart tree into one template namespace
  ([Section 9.2](#92-template-language)).
* Without a cluster, return empty results from `lookup`, and document which
  `.Capabilities` values you use.

### 18.4 Validating Charts

* Run the checks in [Section 16.1](#161-load-time-validation) first. They
  decide whether Helm can load the chart at all.
* Then run the lint rules in [Section 16.2](#162-lint-rules) and report the
  severity of each finding.
* Validate `Chart.yaml` and `Chart.lock` with the JSON Schemas in
  [Appendix A](#appendix-a-json-schema-for-chartyaml) and
  [Appendix B](#appendix-b-json-schema-for-chartlock). The schemas cover
  structure and types only. Some rules, such as unique dependency names, need
  code.

### 18.5 Common Mistakes

| Mistake | Effect | Fix |
|---|---|---|
| `appVersion: 1.10` (not quoted) | Parsed as the number `1.1`, and lint reports an error | `appVersion: "1.10"` |
| `templates/helpers.tpl` without `_` | Its output is treated as manifests | Rename to `_helpers.tpl` |
| `define "fullname"` without a chart prefix | Clashes with a subchart's template of the same name | `define "mychart.fullname"` |
| A list in `values.yaml` that users are expected to extend | User values replace the whole list | Use a map, or document that the list is replaced |
| `kubeVersion: ">=1.25.0"` | Does not match versions such as `1.29.4-eks-1` | `">=1.25.0-0"` |
| `!pattern` in `.helmignore` | Ignores almost everything, including `Chart.yaml` | Do not use `!` patterns |
| A non-chart file in `charts/` | Loading fails | Move it, or start its name with `_` or `.` |
| A CRD in `crds/` that needs changes on upgrade | Helm never upgrades it | Template the CRD, or manage it outside Helm |
| An unknown event in `helm.sh/hook` | The resource is dropped without an error | Use only the events in [Section 11.1](#111-hook-annotation) |
| `helm.sh/hook-weight: 5` (number) | Rejected by Kubernetes; annotation values must be strings | `"5"` |
| `+` in `version` used in a label | Not a valid label value | `replace "+" "_"` |

## Appendix A: JSON Schema for Chart.yaml

This schema (JSON Schema draft 2020-12) describes the structure of a `v2`
`Chart.yaml` after it is converted from YAML to JSON. It is as strict as
`helm lint`: it rejects unknown fields, which Helm itself only warns about.
It does not cover rules that need code, such as unique dependency names, or
the strict SemVer 2 check (the `version` pattern accepts every form Helm
can load). It was tested against the 190 surveyed charts. The only failures
were two charts with the legacy `engine` field.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://helm.sh/schemas/chart/v2/Chart.yaml.json",
  "title": "Helm Chart.yaml (apiVersion v2)",
  "type": "object",
  "required": [
    "apiVersion",
    "name",
    "version"
  ],
  "additionalProperties": false,
  "properties": {
    "apiVersion": {
      "const": "v2"
    },
    "name": {
      "type": "string",
      "minLength": 1,
      "not": {
        "enum": [
          ".",
          ".."
        ]
      },
      "pattern": "^[^/\\\\]+$"
    },
    "version": {
      "type": "string",
      "pattern": "^v?[0-9]+(\\.[0-9]+)?(\\.[0-9]+)?(-[0-9A-Za-z-]+(\\.[0-9A-Za-z-]+)*)?(\\+[0-9A-Za-z-]+(\\.[0-9A-Za-z-]+)*)?$"
    },
    "kubeVersion": {
      "type": "string"
    },
    "description": {
      "type": "string"
    },
    "type": {
      "enum": [
        "application",
        "library",
        ""
      ]
    },
    "keywords": {
      "type": [
        "array",
        "null"
      ],
      "items": {
        "type": "string"
      }
    },
    "home": {
      "type": "string"
    },
    "sources": {
      "type": [
        "array",
        "null"
      ],
      "items": {
        "type": "string",
        "minLength": 1
      }
    },
    "dependencies": {
      "type": [
        "array",
        "null"
      ],
      "items": {
        "$ref": "#/$defs/dependency"
      }
    },
    "maintainers": {
      "type": [
        "array",
        "null"
```

## Appendix D: Differences from Chart API v1

`v2` tools often meet `v1` charts. These are the differences:

| Topic | `v1` (Helm 2) | `v2` (Helm 3 and later) |
|---|---|---|
| `apiVersion` | `v1`, or missing | `v2` |
| Dependencies | `requirements.yaml` | `dependencies` in `Chart.yaml`. `helm lint` reports `dependencies` in a `v1` `Chart.yaml` as an error. |
| Lock file | `requirements.lock` | `Chart.lock` |
| `type` (library charts) | Not available | `application` or `library` |
| `engine` field | Template engine name (`gotpl`) | Not part of the schema. Ignored. |
| Lock digest | Computed from the requirements only, before repository names are resolved | [Section 6](#6-chartlock) |

Helm still loads `requirements.yaml` and `requirements.lock` in a `v2`
chart. It merges the dependencies into the metadata and prints a warning.
New `v2` charts MUST NOT use these files. When Helm packages a `v1` chart,
it keeps `requirements.*` as ordinary files and leaves `dependencies` out of
`Chart.yaml`.

To convert a `v1` chart to `v2`:

1. Set `apiVersion: v2`.
2. Move the `dependencies` list from `requirements.yaml` into `Chart.yaml`.
   Delete `requirements.yaml` and `requirements.lock`.
3. Run `helm dependency update` to create `Chart.lock`.
4. Remove `engine`, if present.
5. Add `type: library` if the chart only has named templates.

## Appendix E: Known Documentation and Implementation Differences

This specification follows the reference implementation. These are the
places where it differs from the Helm documentation:

| Topic | Documentation | Implementation (this specification) |
|---|---|---|
| Unknown `Chart.yaml` fields | "As of v3.3.2, additional fields are not allowed" | Loading ignores them. `helm lint` warns. `helm package` drops them. |
| Chart name rules | The best practices guide says `helm lint` rejects uppercase letters, underscores, dots, and names over 63 characters | `helm lint` only checks that the name is not empty and has no path separator. `helm create` allows `^[a-zA-Z0-9._-]+$` up to 250 characters. |
| `.helmignore` negation | The `helm create` template says `!` negates a pattern. The `.helmignore` guide says `!` has no special meaning. | A `!` pattern ignores every path that does **not** match it ([Section 13](#13-helmignore)). |
| `version` | SemVer 2 | Masterminds semver in non-strict mode (also accepts `v1.2`). `helm lint` warns about non-strict versions. |
| `null` values from parent charts | A `null` removes a key | User-supplied `null`s always remove keys. A `null` that a parent chart sets for a subchart key removes the subchart default only if the user also supplies values for that subchart ([Section 7.2](#72-merging-values-coalescing)). |
| `helm lint` and `import-values` | Not mentioned | `helm lint` does not process `import-values`. |
| String fields | Not mentioned | Whitespace characters are changed to spaces and non-printable characters are removed ([Section 4.2](#42-fields)). |
